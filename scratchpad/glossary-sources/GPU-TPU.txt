## Frame: GPU/TPU & Accelerator Computing — Senior-Level Best Practices

- Memory hierarchy: SRAM/registers >> HBM in bandwidth and latency — the fastest kernel keeps data resident in on-chip memory (TPU VMEM, GPU shared mem/L2) and minimizes round-trips to HBM. This is
why fused kernels (FlashAttention) beat naive op-by-op execution even at equal FLOP counts.
- Host-device transfer overhead: any CPU<->accelerator copy (dataloading, `.item()`/`.cpu()` calls, per-step logging/asserts) is often the real bottleneck, not compute.
  - Use pinned memory and async copy streams to overlap transfer with compute
  - Batch/aggregate host-side syncs instead of forcing one every step
- Mixed precision — bf16 vs fp16: bf16 keeps fp32's dynamic range with fp16's throughput, so it doesn't need loss scaling and is the safer default for large-model training; fp16 is faster on some older
hardware paths but requires dynamic loss scaling to avoid gradient underflow.
- fp8: the newest speed tier (NVIDIA H100+, TPU v5p/Trillium+) — needs per-tensor or per-block scaling and is typically reserved for the largest matmuls (attention QK^T, MLP projections) while master
weights/optimizer state stay in higher precision.
- Numerics discipline: keep a fp32 (or bf16) master copy of weights/optimizer state even when compute runs in a lower precision — accumulation error compounds over millions of steps and is invisible until a
loss spike or divergence far into a run.
- Data parallel (DP): replicate the full model per device, shard the batch — simplest mental model, but activation memory scales with per-device batch size and it needs an all-reduce of gradients every step.
Hits a wall once the model itself no longer fits on one device.
- Tensor parallel (TP): shard individual layers' weight matrices across devices (Megatron-style column/row-parallel linear layers). Cuts per-device memory but synchronizes *inside* every forward/backward pass,
so it needs high-bandwidth, low-latency interconnect (NVLink / TPU ICI) — generally kept within a node/pod.
- Pipeline parallel (PP): shard the model by layer/stage across devices and stream micro-batches through. Communication is coarser (activations between adjacent stages only), which tolerates slower
interconnects across nodes, but introduces pipeline-bubble overhead — needs enough micro-batches to keep all stages busy.
- Choosing a strategy: DP when the model fits per-device and you want throughput/simplicity; TP for within-node scaling when a single layer is too large; PP for scaling across nodes with slower links.
Production LLM training composes all three ("3D parallelism") plus ZeRO/FSDP-style parameter/optimizer-state sharding to remove redundant memory.
- Profiling workflow: start from the timeline trace, not intuition — first classify the bottleneck as compute-bound (SM/MXU utilization high, kernels back-to-back), memory-bandwidth-bound, or communication-
bound (visible gaps waiting on collectives).
- What to actually look for in a trace:
  - Idle gaps between kernels — usually host-side Python overhead or unfused ops
  - Disproportionately long all-reduce/all-gather bars — comm-bound, check whether they overlap with compute
  - Many small/short kernels dominating wall time — launch-overhead-bound, a fusion candidate
  - Step-to-step timing variance — a signal of stragglers, thermal throttling, or resource contention
- Practical tools: PyTorch Profiler + Chrome trace viewer/TensorBoard, NVIDIA Nsight Systems (timeline) and Nsight Compute (per-kernel detail) for CUDA, JAX/XLA's built-in profiler + XProf/TensorBoard
for TPU. Always profile a few warmed-up steps — the first includes compilation/warmup and skews the numbers.
- RAII in ML systems: CUDA/C++ runtime code wraps raw resource handles (streams, device memory, cuBLAS/cuDNN handles) in RAII classes so destructors free them on scope exit or exception. Matters
because accelerator memory leaks degrade a long-running training job silently rather than crashing immediately.
- Move semantics: avoid unnecessary deep copies of large device-memory-backed buffers passed between C++ layers of a runtime — `std::move` and move constructors transfer ownership without copying,
which is significant when a "tensor" wrapper object represents gigabytes on the device.
- Templates in CUDA/ML runtimes: kernels are commonly templated on dtype (fp16/bf16/fp32) and tile/block size so the compiler emits specialized, branch-free code per instantiation instead of paying a
runtime dispatch cost — this is why CUTLASS/cuDNN-style APIs look template-heavy.
- C++ fundamentals to prioritize before CUDA/XLA: value vs. reference semantics, ownership (`unique_ptr`/`shared_ptr` vs. raw pointers), templates, and RAII. These four show up constantly in kernel
wrapper code and runtime internals — more load-bearing early on than deep OOP class hierarchies.

8.1.2 The High Bandwidth memory bottleneck in standard attention
To understand why Flash Attention is necessary, first analyze the standard implementation of the attention mechanism

The core of attention
    1. calculate the dot product of Query (Q) and Key (K) matrices, Score (S) = Q @ (K) dot (T)
    2. apply softmax to the score to get weights (P), P = softmax(S)
    3. multiply the attention weights P by the value (V) matrix to get output, O = P @ V

For a context length, N = 8192, (N, d) (S, P) = (N, N) -> 8192 x 8192 x 4 bytes (32-bit floats) ~~ 268 megabytes
... for a modern context length N = 128k ... >65GB for a single attention head
    This is the throughput problem transferring between memory, not the computational throughput
** the entire S matrix must be written to HBM after the first matrix multiplication, read back from HBM, writes back to HBM, reads again for final matrix multiplication **
-> fast onchip SRAM and slower offchip HBM is the bottleneck

2.7 The Universal Pattern: From nD to 1D
Whether you’re working with 1D vectors, 2D matrices, 3D tensors, or even higher-dimensional data, the pattern remains the same:

Calculate your thread’s unique coordinates using blockIdx and threadIdx
Apply boundary checks to ensure you don’t access invalid memory
Linearize the nD coordinates into a row-major 1D memory index using stride calculations (this matches the layout used by C, NumPy, and PyTorch)
Perform your computation on the data at that index
That third step is often called "linearizing" or "flattening" your index. Because PyTorch, NumPy, and plain C default to row-major layout, the stride formulas you’ve seen throughout this chapter follow that convention.

This is the foundation of all CUDA programming. Master this pattern, and you can parallelize operations on data of any dimensionality.

2.8 Summary
A CUDA program consists of two main parts: host code that runs on the CPU and orchestrates the process, and device code (kernels) that runs in massive parallel on the GPU.
The terms Host and Device are the official CUDA terminology for the CPU and GPU, respectively. They have separate memory spaces.
Data must be explicitly transferred between host (RAM) and device (VRAM) memory using cudaMemcpy. This transfer is a potential performance bottleneck.
GPU memory is managed with cudaMalloc and cudaFree, analogous to C’s malloc and free for host memory.
A kernel is a C++ function marked with global that is launched from the host and executed by many threads on the device.
CUDA organizes threads into a two-level hierarchy: threads are grouped into blocks, and blocks are organized into a grid.
Each thread calculates a unique global index using built-in variables (blockIdx, threadIdx, blockDim, gridDim) to determine which piece of data it is responsible for processing.
Essential C concepts like pointers (*) are fundamental to CUDA, as they are used to manage memory addresses on both the host and device.
A simple CUDA program can be compiled from the command line using the CUDA compiler (nvcc).

5.1.1 Decoder-only transformer architecture (GPT)
    - encoder-decoder used for translations
    - encoder-only used for classificaiton

Transformer Terminology:
    -> Head: A single attention computation that projects inputs to queries, keys, and values, computes attention scores, and
produces an output. Each head learns to focus on different relationships between tokens.
    -> Multi-head attention: Multiple heads running in parallel, their outputs concatenated and projected back to the model dimension.
This allows the model to attend to information from different representation subspaces simultaneously.
    -> Block (or layer): One complete transformer unit containing multi-head attention, a feed-forward network, and the residual
connections and layer normalization that wrap them. Our model stacks 8 of these blocks.
    -> Model: The complete transformer: token embeddings, position embeddings, a stack of blocks, final layer normalization, and the
output projection to vocabulary logits (the raw, unnormalized scores for each token in the vocabulary before softmax converts them
to probabilities).

We also need to be precise about tensor dimensions. Throughout this chapter, our primary activation tensor has shape (batch,
sequence_length, embedding_dim) or (B, T, C) in code:

B (batch): Number of sequences processed in parallel (16 in our setup)
T (sequence length): Number of tokens per sequence (64 in our setup)
C (channels/embedding dimension): Size of each token’s representation (128 in our setup)

5.2 Inference: Theory and Optimization

    - inference is fundamentally different from training.
    - inference generates tokens one at a time through autoregressive sampling
    - **APPLY KV-CACHING AND OTHER OPTIMIZATION**

5.2.1 Optimizing Autoregressive Generation
    - Inference flips our computational paradigm completley.
        - instead of processing 64 tokens in parallel, we generate one token at a time (based on all
previous tokens; hence KV cache)
    - previous training scale was for learning purposes but inference scaled to reflect production like
workloads (768 dimensional embeddings, 24 layers)
    - at scale, we can better see the performance improvements using cuda kernel level optimizations

5.2.1 KV Cache: Avoiding redundent computation
    - KV cache stores key-value tensors from previous tokens during autoregressive generation,
avoiding recompute for each new token
    - how does it work?
         During each generation step, we compute the new token’s key and value vectors and append
them to our cache. When computing attention, the new token’s query attends to all cached keys and
values, transforming the operation from GEMM (recomputing everything) to GEMV (one query against
cached data).

5.2.2 GEMV-Dominated Inference operations
    - KV cache transforms computational patterns from matrix-matrix to matrix-vector
        - we compute attention for one new position against all previous positions

Because T = 1 during generation (we process a single new token at a time), the returned tensor
already matches the narrow blue column. From there the attention heads run matrix-vector products
against the cached keys and values instead of full matrix-matrix multiplies, so memory bandwidth
becomes the primary bottleneck.

5.2.2 cache vs recomputation memory trade-offs
    - KV cache trades memory for computation; compute only new ones
        - The longer the sequence, the more computation we save, but the more memory we consume.
This trade-off becomes critical when serving models at scale.

5.2.2 Mixture of Experts in Inference: Sparse Activation
    - What is it? Mixture of Experts (MoE) is an architectural pattern that replaces a single dense
feed-forward layer with multiple parallel feed-forward networks called "experts." Each expert has
identical architecture (the same layer sizes and activation functions) but different learned weights. A
router network scores each expert for a given input and selects the top-k to actually run. The term
"expert" is a metaphor from the machine learning literature: through training, each network tends to
specialize in different input patterns, becoming an "expert" at processing certain types of tokens.
This specialization emerges from optimization, not from explicit design - the router and experts co-
adapt so that tokens get routed to whichever expert produces the best predictions. 

Why should I care? MoE allows models to scale to massive parameter counts (trillions) while keeping
inference costs manageable. Only a small fraction (typically 2-4 experts out of hundreds) are active
per token, dramatically reducing compute requirements.

How does it work? For each token, a router network computes scores for all experts, selects the top-
k highest scoring experts, normalizes their weights, and combines their outputs. During inference, this
sparse activation means you’re only computing ~1% of the model’s total parameters per token.

The routing process involves several key steps:

Router Computation: A linear layer transforms each token’s embedding into expert scores
Softmax Normalization: Convert scores to probabilities across all experts
Top-K Selection: Choose the k experts with highest probabilities
Load Balancing: Re-normalize probabilities among selected experts
Expert Execution: Run each selected expert on the token
Output Combination: Weighted sum of expert outputs
This sparsity creates unique optimization opportunities for CUDA kernels, particularly in the top-k
selection and routing computation. figure 5.10 illustrates the top-k selection process that determines
which experts process each token.

5.2.2 CUDA Optimized MOE Routing
- hand the heavy lifting to CUDA kernels: score experts in PyTorch, offload the softmax and top-k
work to CUDA, then combine the selected expert outputs back to Python with a handful of tensors

5.2.2 GEMV vs GEMM: the fundamental shift
    Training Pattern (GEMM):
    
    Process 8 tokens simultaneously: [4,8,4] @ [4,4] = [4,8,4]
    Attention computes full 8×8 matrices
    High arithmetic intensity
    All positions computed in parallel
    Inference Pattern (GEMV):
    
    Process 1 new token: [1,1,4] @ [4,4] = [1,1,4]
    Attention: 1 query against cached keys
    Lower arithmetic intensity per step
    Sequential token generation
    Memory bandwidth critical for cache access

5.3.2 GEMV: The inference workhorse
    - Matrix-vector multiplication for single-token processing
Training uses GEMM (matrix-matrix): [B, T, D] @ [D, D] -> [B,T,D]
Inference uses GEMV (metrix-vector): [1, 1, D] @ [D, D] -> [1, 1, D]

Remember, at inference, we process one token outputs as they arrive: GEMV (inference, 1 new
token)
GEMM (training, T=64 tokens):
Q[64, 128] @ K.T[128, 64] = Scores[64, 64]
-> 64 * 64 * 128 = 524,288 FLOPs
-> High arithmetic intensity, compute-bound

GEMV (inference, 1 new token):
q[1, 128] @ K.T[128, 64] = scores[1, 64]
-> 1 * 64 * 128 = 8,192 FLOPs
-> Low arithmetic intensity, memory-bound

GEMV vs GEMM kernel strategy
- GEMM optimized for compute-bound arithmic intesity using shared memory tiling

- GEMV is memory bound by loading, not computing the dot product

5.3.2 topK for mixture of export (MoE) routing
where k = 2, we select the 2 highest scorees

TopK parallelizes across batch elements. Each token in the batch needs its own independent
routing decision, so we assign one CUDA block per token. Within each block, a single thread scans
through all expert scores and maintains a small sorted buffer of the k best candidates.

5.3.2 Design Decision: why naive insertion sort
- Why this works for MoE:

k is tiny (k=2 or k=4 typically)
n is small (n=8 experts in our example)
Overhead of parallel algorithms > benefit
Total comparisons: 8 * 2 = 16 (trivial)
Performance: For k=2, n=8:

Our kernel: ~2 μs
Parallel reduction: ~15 μs (synchronization overhead)
As k grows (k=64 for larger MoE), you’d switch to parallel approaches. But for typical MoE (k=2),
simple wins.

Note on alternative methods:
Option 1: Parallel reduction (like finding max)

// Multiple rounds: find max, mask it, repeat k times
__shared__ float smax[256];
for (round = 0; round < k; round++) {
    parallel_max_reduce(input, smax);
    top_k[round] = smax[0];
    input[argmax] = -INF;  // Mask found value
}

Overhead: thread synchronization, shared memory management Good for: Large k (k > 32)

Option 2: Sorting networks
// Bitonic sort: fixed comparison pattern
// Compare-exchange pairs in parallel
if ((i & mask) == 0)
    compare_and_swap(arr[i], arr[i ^ mask]);

Overhead: Complex indexing, works well for power-of-2 sizes Good for: k close to n

Option 3: Insertion sort (our choice)
// Simple: one thread scans all values
for each value in input:
    if value > smallest_in_top_k:
        insert_sorted(value, top_k)

Works best for: Small k (k=2 in our case)
